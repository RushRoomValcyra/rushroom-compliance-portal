## Discovered While Building

- **`materialiseConfiguration` writes its edges blind** (PROP-067). The edge insert's error is never checked, and it re-inserts the deeper edges under their original parents, where those links already exist — so the unique index can reject the whole batch and the materialised SKU silently comes out empty. Untouched apart from carrying `is_reference`; not used in production (0 Dynamic BOMs).
- **The BOM tree export has no Hub/Site column** (PROP-067, found adding the *Reference child* column). The crew-list idea under PROP-056 needs it; it is one entry in `BOM_TREE_COLUMNS` now that rows can carry the edge.
- **`portal-api/index.ts` is 5,600 lines with every action inline** (PROP-067). This build started `portal-api/handlers/` with one file; moving existing actions out is its own job, not a side effect of a feature.
- **Changing a bought part to Assembled can now be refused** (PROP-067). The component trigger refuses any Type/Sourcing change that would leave its current children breaking the rule — correct, but the edit form only shows the message after Save. Offering the right next step there (e.g. "Convert to sub-assembly") is a small follow-up.
- **A Postgres view bypasses RLS by default, and Supabase's linter is the only thing that says so** (PROP-066). `stock_levels` was written as an ordinary view over `stock_ledger` and `storage_locations`, both correctly protected by `is_active_workforce()`. A view runs as its *owner*, not the querying user, so it returned the entire stock position to any authenticated caller regardless of those policies. Nothing in the migration looked wrong and no test would have caught it — it surfaced only as a `security_definer_view` ERROR from `supabase advisors`. Fixed with `alter view … set (security_invoker = on)`. The general lesson: **every view over an RLS-protected table needs `security_invoker = on` explicitly**, and the advisors should be run after any migration that adds one. Worth auditing whether the compliance portal has views in the same shape.
- **Guard errors are a UI surface, and swallowing them wastes the work** (PROP-066). The structure triggers raise messages that name the bin and state the correct alternative ("Bin X still holds stock. Move every item out before retiring it."). The server layer was throwing `new Error("Location could not be deactivated")` over the top of them, so the operator would have seen the useless half. Server functions that call a guarded write should surface `error.message`, not replace it.
- **The Parts tab still has no `+child`** (PROP-062). Making parts expandable exposed that a part holding structure can be *read* there but not *edited* there — you have to find it under an assembly. Deliberately not changed: adding a structure button to 86 catalogue rows is a separate decision, not a side effect of an expand control.
- **There is still no way to replace a part in an EXISTING tree** (PROP-060). Substitution happens at copy time, which is where the S/M/L value is. Swapping a child of an assembly you already have still means remove + add, losing the quantity, reference designator, order and fitting stage on that link. The server piece would be small — close the edge, open an identical one pointing elsewhere — and `pickComponentModal` already exists for the UI.
- **A deep copy takes no documents, drawings or images** (PROP-059) — the same as the single-node ⧉ always did, and stated in the dialog rather than left to be discovered. Whether a copied assembly should inherit its original's document links is a real question; right now it inherits none.
- **`copyAssembly` is not transactional** (PROP-059). Components are written, then the edges in one insert. If the edge insert fails the components exist and the error says so, but nobody cleans them up. Supabase's REST client has no multi-statement transaction; doing this properly means a Postgres function.
- **Phantoms are not blow-through** (PROP-058) — **decided 2026-10-06: never dissolved.** A phantom (now shown as **Kit**) is a pick group: its children are drawn from stock and picked together under it. Cheap to audit — count rows per table and ask why the empty ones are empty.
- **`getComponentChangelog` silently drops every document event** — it selects `created_at` from `component_documents`, which has `uploaded_at`. PostgREST rejects the query, and the handler checks only `histRes.error`, so the merge proceeds with zero document entries and the Change Log looks complete. Verified in production: `ERROR 42703: column "created_at" does not exist`. A one-line fix, but the shape is the lesson — a parallel fetch whose error is unchecked degrades to an empty list, which is indistinguishable from "nothing happened". **Fixed by PROP-043 (2026-09-16)** — kept here for the shape, not the bug: a parallel fetch whose error goes unchecked degrades to an empty list, which is indistinguishable from "nothing happened". Every source in that handler now reports its own failure.
- **Fields that accept input and display nowhere** — three found on 2026-09-16 alone: `custom_specs` written to a JSONB column no screen rendered, `manufacturer_part_number` silently dropped by the `upsertComponentMetadata` whitelist, and `bom_components.description` collected at create time but never selected by `listComponents` or `getBom`. Each looked like it worked. Worth one pass comparing every column written by a form against the screens that render it — the failure mode is silent by construction, so it will not surface as a bug report.
- **Measure the boundary before diagnosing performance** — 2026-09-16 cost four attempts. Three fixes were reasoned from reading the code (signed-URL round trips, a redundant action, unlazy thumbnails); all were real improvements and none were the cause, which turned out to be a Supabase API Gateway degradation, confirmed by Supabase. The check that settled it took one command: time the endpoint from outside the app and compare it against another service on the same project. Do that first next time — if an endpoint that returns 401 without touching the database takes seconds, the application is not the subject.
- **Component detail panel makes ~14 parallel API calls on open** — one `Promise.all` of separate actions, each a full edge-function invocation with p50 ~460 ms. Browsers cap concurrency per origin, so it is several waves before anything renders. v230 removed one call and fixed the per-image URL signing behind two of them, but the shape is the cost: a single `getComponentDetail` action returning the whole panel payload would replace fourteen invocations with one. Worth doing before the part count grows.
_Found mid-build, too small or too tangential for a PROP, too real to drop. Promote to Next, or delete once it stops mattering._

- **`assets/app.js` shared-state scoping** *(now four occurrences — worth acting on)* — `bomTreeView` holds list state in one closure while the modals that need it (`openAddChildModal`, `openComponentDetail`, `openMoveModal`) are sibling functions outside it.
