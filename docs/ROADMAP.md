## Discovered While Building
- **A deep copy takes no documents, drawings or images** (PROP-059) — the same as the single-node ⧉ always did, and stated in the dialog rather than left to be discovered. Whether a copied assembly should inherit its original's document links is a real question; right now it inherits none.
- **`copyAssembly` is not transactional** (PROP-059). Components are written, then the edges in one insert. If the edge insert fails the components exist and the error says so, but nobody cleans them up. Supabase's REST client has no multi-statement transaction; doing this properly means a Postgres function.
- **Phantoms are not blow-through** (PROP-058). In every other PLM a phantom assembly is transparent on explosion: exploding a BOM skips the phantom level and attaches its children to the phantom's parent, so nothing ever tries to pick or build it. Nothing in this portal flattens them — `getBom`, the tree, the exports and the roll-up quantities all treat a phantom as an ordinary level. That is fine while phantoms are only a grouping label, and becomes wrong the moment anything explodes a BOM to pick from. Decide it before the first pick list, not after.
- **A phantom's `make_or_buy` is meaningless but still required-ish** (PROP-058). The sourcing dropdown offers purchased / manufactured / assembled / subcontracted, and none of them is true of a node that is never built. It defaults to something and nobody will notice, which is exactly the pattern worth not repeating.
- **Scroll-to-hide chrome is not available here** (PROP-057). The obvious pattern — hide the header on scroll down, reveal on scroll up — cannot work on the BOM screen: `treeArea` sizes itself to `innerHeight - its own top` and scrolls internally, so the window never scrolls and there is no gesture to listen for. Worth remembering before proposing it for any other screen with an inner scroll region.
- **Nothing derives the two crew lists yet** (PROP-056). The stage is captured and counted, but there is no "give me the hub build list" or "give me the site installation kit" output — the user chose badge-and-counts only for this pass. The exports (`BOM_EXPORT_COLUMNS`, `BOM_TREE_COLUMNS`) and a tree filter are each a small addition on top of the column now that it exists.
- **Stage is not inherited down a sub-assembly** (PROP-056). A child inside a hub-built sub-assembly is still its own unset edge. That is deliberate for a first pass — whether "hub" should cascade, and whether a site-fitted part inside a hub sub-assembly is legal, is a semantics decision better made after the feature has been used once.
- **The +child tray does not offer the stage** (PROP-056). It is set afterwards from the tree, so a freshly linked part starts unset. Adding a third control beside Qty and Ref is easy; worth doing only if the counts show people forgetting.
- **The Studio tab's body copy still says "planner"** — the screen header ("Saved planner keys"), the intro paragraph and the field hints all use the old vocabulary, which now disagrees with the tab above them. Deliberately not swept: `source_type` / `source_key` are column names and "planner source key" is the term they encode, so aligning the copy is a naming decision rather than a find-and-replace.
- **The picker still offers parts that are already children of this parent** (PROP-051). Adding one produces a server-side duplicate-edge error, which now surfaces per row instead of being a dead end — but the honest fix is to mark them in the list (“already a child”) rather than let them be picked. Needs the parent's current edges, which the modal does not receive today.
- **The move-child picker has the same blind list** (PROP-050). `listMoveTargets` renders part number + name with no picture, and `thumbBox()` now exists to fix it in one line. Left alone deliberately — the request named the add-child picker — but the two should not stay different for long.
- **Asset cache versions had drifted apart** — `index.html` carried `styles.css?v=255`, `config.js?v=253` and `app.js?v=257` at the same time, so a bump could refresh some files and not others. All non-favicon tags are now on one number (258) across index/supplier/reset/verify; keep them moving together.
- **Per-part sheets carry only what `listComponents` returns** (PROP-049). Specifications, linked drawings, documents and images beyond the first are all absent, because putting them in would mean one API call per part at export time. The seam is `BOM_DETAIL_COLUMNS` — widening it is cheap once a `getComponentDetail` batch action exists, which the roadmap already wants for the panel's 15 parallel calls. Same fix serves both.
- **Sheet size, scale and projection angle are now collected and displayed nowhere** — the drawing rail row showing them was removed on request (v252), but the create modal still asks for all three and `extractDrawingMeta` still reads them off the title block. That is the "accepted and displayed nowhere" pattern that produced the `custom_specs`, `manufacturer_part_number` and `description` defects. Two honest resolutions: drop the three inputs and the AI keys, or surface the fields somewhere that earns the space. The columns stay in `drawings` either way, so nothing already captured is lost.
- **A drawing can be approved and released with no file at all** — `setDrawingStatus` enforces the transition order (draft → checked → approved → released) but never checks that a revision exists. Production holds a drawing at status `approved` with zero revisions: an approved drawing that does not exist. For a compliance record that is worse than an unapproved one, because the status asserts something was reviewed. Fix is a guard in `setDrawingStatus` (and arguably a CHECK): leaving `draft` should require at least one revision, and `released` should require the current revision to be the one being released. Found 2026-09-17 in a user screenshot.
- **Two buttons named "Open" in the drawings flow mean different things** — in a part's Drawings row, *Open* opens the drawing's detail overlay; inside that overlay, *Open* on a revision opens the file. One is nested in the other. Captured in the IDEAS entry for drawing viewing.
- **Audit every screen for inputs that demand data the UI never shows** — Status Overview asked for a component UUID that appears nowhere in the portal. It is the third feature found this month that worked correctly behind a door nobody could open (drawings in the Documents tab, the Documents library revision path, this). The cheap check: for every free-text input, ask where a user is supposed to obtain that value. If the answer is "the database", the feature has no users and its empty tables are not telling you it is unwanted.
- **A written-but-never-read audit event is the worst failure shape in this system, and it has now happened twice** — `getComponentChangelog` filtered history to `["created","updated"]`, so drawing events and `document_revised` were stored correctly and excluded by the query that displays them. Both times the write side was carefully built and the read side was not revisited. `tests/changelog-events.test.mjs` now asserts the two lists agree. The general lesson is wider than the changelog: whenever a new enum value, column or category is introduced, the code that READS it is a separate change from the code that writes it, and nothing fails loudly when only one is made.
- **Every AI call in the codebase runs on opus** — `SCAN_MODEL` is used by `suggestFileMetadata`, `suggestComponentMetadata`, `suggestDocumentVersion`, `suggestStandardMetadata` and `suggestClassifications`, all of which CLAUDE.md classifies as cheap metadata work that must not use opus. PROP-046 introduced `META_MODEL` (haiku) and moved one action onto it. Migrating the rest is a small, contained change with a direct cost saving, and nothing depends on it first.
- **Product BOM and Manufacturing BOM are sub-tabs of "As Operated"** — found while placing the DRAWINGS tab. The core engineering surface is filed under a compliance-document heading, which is the same discoverability failure PROP-044 fixed for drawings, one level up. Drawings went top-level; the BOM did not, because that is an information-architecture change and not this build's scope.
- **Account tables bypass `makeTdb` and hand-write their `.eq("organization_id")`** — `memberships`, `invitations` and `ai_usage_events` cross the tenant boundary by design, so each call site scopes by hand. They are now allowlisted in `tests/tenant-tables.test.mjs` with reasons, but the hand-written scoping itself has never been audited call site by call site. Worth one pass.
- **The component panel now makes 15 parallel API calls** — PROP-045 added `listDrawings` to the existing 14. The single `getComponentDetail` action already recorded below is now more clearly worth doing than when it was first noted.
- **The Documents library has no route back to the parts that use a document** — PROP-044 fixed the part→document direction, so a drawing can now be attached and revised without leaving the part. The reverse is still blind: standing in the Documents tab, nothing says which BOM nodes link the document you are about to revise, even though `addDocumentVersion` now audits every one of them. The data is already assembled (`shared_with` in `getComponentDocuments`); it is a rendering job, not a new query.
- **Nobody had ever attached a component document** — production held 0 `component_documents` rows on 2026-09-16, which is how PROP-044 was found. Worth a standing check: a feature with zero rows after months is not a feature with low usage, it is one with an unreachable entry point. Cheap to audit — count rows per table and ask why the empty ones are empty.
- **`getComponentChangelog` silently drops every document event** — it selects `created_at` from `component_documents`, which has `uploaded_at`. PostgREST rejects the query, and the handler checks only `histRes.error`, so the merge proceeds with zero document entries and the Change Log looks complete. Verified in production: `ERROR 42703: column "created_at" does not exist`. A one-line fix, but the shape is the lesson — a parallel fetch whose error is unchecked degrades to an empty list, which is indistinguishable from "nothing happened". **Fixed by PROP-043 (2026-09-16)** — kept here for the shape, not the bug: a parallel fetch whose error goes unchecked degrades to an empty list, which is indistinguishable from "nothing happened". Every source in that handler now reports its own failure.
- **Fields that accept input and display nowhere** — three found on 2026-09-16 alone: `custom_specs` written to a JSONB column no screen rendered, `manufacturer_part_number` silently dropped by the `upsertComponentMetadata` whitelist, and `bom_components.description` collected at create time but never selected by `listComponents` or `getBom`. Each looked like it worked. Worth one pass comparing every column written by a form against the screens that render it — the failure mode is silent by construction, so it will not surface as a bug report.
- **Measure the boundary before diagnosing performance** — 2026-09-16 cost four attempts. Three fixes were reasoned from reading the code (signed-URL round trips, a redundant action, unlazy thumbnails); all were real improvements and none were the cause, which turned out to be a Supabase API Gateway degradation, confirmed by Supabase. The check that settled it took one command: time the endpoint from outside the app and compare it against another service on the same project. Do that first next time — if an endpoint that returns 401 without touching the database takes seconds, the application is not the subject.
- **Component detail panel makes ~14 parallel API calls on open** — one `Promise.all` of separate actions, each a full edge-function invocation with p50 ~460 ms. Browsers cap concurrency per origin, so it is several waves before anything renders. v230 removed one call and fixed the per-image URL signing behind two of them, but the shape is the cost: a single `getComponentDetail` action returning the whole panel payload would replace fourteen invocations with one. Worth doing before the part count grows.

- **`assets/app.js` shared-state scoping** *(now four occurrences — worth acting on)* — `bomTreeView` holds list state in one closure while the modals that need it (`openAddChildModal`, `openComponentDetail`, `openMoveModal`) are sibling functions outside it. None of these are caught by `node --check` or an esbuild parse, because they are all valid syntax. `openComponentDetail` is now long enough that declaration order is not visible while editing it — the fix is to hoist the shared state deliberately and split that function.
